### WF-android:002 — Scheduled SMS reminder (alarm → worker → send) [scheduled/background]
**Trigger:** Exact `AlarmManager` alarm fires for an enabled `SchedulerConfig` on a given weekday.
**Steps:**
1. `AlarmScheduler.scheduleAllAlarms()` cancels ALL config×7-day alarms, then re-schedules enabled configs for ALL 7 days (requestCode = `configId*10 + dayOfWeek.value`); past targets roll to +1 week → `AlarmScheduler.kt:18,50,60`
2. Alarm → `SmsAlarmReceiver.onReceive()` enqueues unique `SmsSchedulerWorker` keyed `sms_config_{id}_{today}` (`ExistingWorkPolicy.KEEP`), then re-schedules all alarms via `goAsync()` → `SmsAlarmReceiver.kt:18,31,38`
3. `SmsSchedulerWorker.doWork()`: **retry cap first — `runAttemptCount >= 2` ⇒ high-importance error notification + `Result.failure()`, no send** (`SmsSchedulerWorker.kt:60-67`); read SIM `subscriptionId` from AppSettings, build `AndroidSmsProvider` + `SmsReminderService`; **take foreground for the whole batch with a PER-WORKER notification id `300 + configId`** (a shared id let one worker's completion strip the other's foreground protection — two same-minute configs run as parallel workers) (`:44,81-89`) → `waitForCallToEnd(batchNotificationId)` (re-titles the SAME notification, never a second one) → load config, skip if disabled, **skip if `config.dayGroup != effectiveDayGroup`** (holiday-aware), `computeWindow` → `SmsSchedulerWorker.kt:37,60-121`
4. `SmsReminderService.execute()` — **serialized process-wide by a companion `Mutex`** (`:36-41,284`), then `executeInternal`: resolve **shift type** from the reminder type (`AdminAdvance ⇒ Administrative`, else `Operational`, `:59-60`); resolve template; query `getByDateRangeAndType()` (active + typed, `:71`); bulk-load volunteers, **shiftIds with ANY `SmsLog` row for this reminder type** (`getShiftIdsWithAnyRow`, `:84`), locations (SameDay **and** AdminAdvance); per shift check volunteerId/approval/phone/snapshot-dedup → **point re-check `existsByShiftIdAndReminderType` immediately before dispatch** (`:128`) → build message (SameDay appends the location block; AdminAdvance appends mission + vehicle blocks, `:154-168`) → **write-ahead: INSERT `SmsLog` with status `Dispatched` BEFORE handing the message to the radio** (`:172-180`) → `smsProvider.sendSms()` → **disarm `writeAheadId`** so no later error can re-label a delivered message (`:188-189`) → `when (outcome)`: CONFIRMED ⇒ update row to `Success` + `SmsSentAt`; FAILED ⇒ update row to `Fail`; UNKNOWN ⇒ leave the row `Dispatched` and **count it as sent** (`:191-214`) → 500ms inter-SMS delay → insert `SchedulerRunLog` (UNIQUE-guarded) → `SmsReminderService.kt:36-280`
5. `runDuplicateDetector(runStart)` — queries `findDuplicateDispatches(since = runStart − 60s)` for any `(ShiftId, ReminderType)` with >1 **non-Fail** row created in this run window, and raises a high-priority notification if found. **Log-only and bounded to this run**, so historical rows (including the original incident's) and cross-run manual re-sends never alert, and a detector error can never map to `Result.retry()` (`SmsSchedulerWorker.kt:123,148-165`).
6. Worker shows summary notification (channel `magav_sms_summary_channel`, id 100) → `SmsSchedulerWorker.kt:250-256`
**State transitions:** `SmsLog` row goes `Dispatched → Success | Fail`, or **stays `Dispatched`** when the send window closed without confirmation; `Shift.SmsSentAt` set on CONFIRMED only; `SchedulerRunLog` upserted (dup = silent skip via UNIQUE).
**Error handling:** `CancellationException` is **rethrown first in every touched catch** (a stopped worker must stop dispatching, not keep going unlogged); worker outer catch → `Result.retry()` (capped at one executing retry); per-config catch in `checkAllConfigs` continues; notification and `SmsSentAt` failures are logged, never fatal; the per-shift catch marks the write-ahead row `Fail` **only while `writeAheadId` is still armed** — i.e. only for an exception that happened before the send returned.

### WF-android:008 — Auto-callback-to-gate (eligible incoming call → reject + dial Gate) [event-driven] (horizontal: WF-004)

2. **OFFHOOK / IDLE** → `cancelAlarm()` (a battery optimization, NOT correctness — the fire-time re-check is authoritative). → `CallbackPhoneStateReceiver.kt:41-44`
3. **Alarm fires (+20s)** → `CallbackAlarmReceiver` `goAsync()`+IO → if `isDatabaseReady` && `tm.callState == CALL_STATE_RINGING` → `CallbackLogic.rejectAndDialGate()`. This single state re-check is THE authoritative gate (answered⇒OFFHOOK, hung-up⇒IDLE, busy⇒OFFHOOK; only still-ringing passes) — no state machine, no epoch, no wakelock. → `CallbackAlarmReceiver.kt:20-37`

**Error handling:** every entry point is fail-safe — any exception / missing data / missing permission ⇒ does NOTHING (never crashes, never dials the wrong number).
