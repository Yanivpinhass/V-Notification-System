# Admin Shifts — Plan Validation Report

Generated by an adversarial multi-agent validation: a planning agent produced a full implementation plan from `admin-shifts-planning-prompt.md`, then four independent validators (correctness / completeness+parity / data-safety+regression / UI+contract) stress-tested it against the live code.

## Verdict: NOT READY TODAY — resolvable to READY WITH FIXES

The core design is sound: the `WeekdayAdvance`-reuse scheduler timing is **provably correct** (no double / no missed sends; Sunday shift → Friday; holiday roll-back), and parity/migration/dedup discipline is strong. But **two P0 defects** must be resolved on paper before any coding, plus a factual correction.

## Factual correction (already applied to the prompt)

- **Room DB is at `version = 9`, not 8.** `MIGRATION_8_9` already exists (added the `CallbackConfig` table). The admin migration is **`MIGRATION_9_10`, version → 10**; both `addMigrations(...)` sites list six migrations to extend.

## P0 blockers (must fix before implementation)

### P0-1 — `SchedulerRunLog.ConfigId` is a FOREIGN KEY → `SchedulerConfig(Id)`
- Evidence: `DbInitializer.cs` ~202 (`FOREIGN KEY (ConfigId) REFERENCES SchedulerConfig(Id)`); Android `SchedulerRunLogEntity.kt` Room `@ForeignKey`.
- Impact: storing the admin advance config in a **separate table** (the prompt's earlier lean) makes the admin run-log INSERT reference a non-existent `SchedulerConfig` id → on Android it **throws → dedup row never persists → duplicate admin SMS every scheduler tick**. (.NET may not enable `PRAGMA foreign_keys`, so this is invisible in web testing and bites only on Android.)
- **Fix (recommended):** store the admin advance as a **REAL row inside `SchedulerConfig`** (`ReminderType='AdminAdvance'`, `DayGroup='SunThu'`) and filter that row out of the operational config GET, bulk-PUT exact-match validation, and React grouping. This keeps the FK valid AND makes the firing gate (`DayGroup == effectiveDayGroup`) work verbatim — collapsing three P1 findings too. (Alternative: separate table + a dedicated `AdminSchedulerRunLog` with no FK.)

### P0-2 — Excel-import hard-delete permanently destroys admin shifts
- Evidence: `ShiftsImportService.cs` ~109 `DeleteManyAsync<Shift>(ShiftDate >= min && <= max)`; Android `ShiftDao` `deleteByDateRange`/`deleteByDateFrom`/`deleteOlderThan`. No `ShiftType` (or `IsCanceled`) filter — a **hard DELETE**, not soft-cancel.
- Impact: an operational Excel import over a date range containing admin shifts **permanently deletes** those admin shifts. This path was missing from the query-isolation enumeration.
- **Fix:** add `AND ShiftType = 'Operational'` to every import delete + the delete DAO family; regression-test that admin rows survive an overlapping import.

## P1 — should fix before shipping (most collapse once P0-1 → in-table config)

- Firing gate needs a hand-written `SunThu` check on a separate table (auto-fixed by in-table config).
- Android alarm dispatch + reschedule not actually wired (`configId=-2` sentinel routes nowhere; `AlarmScheduler` only iterates `SchedulerConfig`) — auto-fixed by in-table config.
- `execute()` is typed to `SchedulerConfig`/`SchedulerConfigEntity` — "reuse" needs parametrization or a dedicated admin execute — auto-fixed by in-table config.
- Template migration to EXISTING installs: seeding runs only on fresh DBs; admin templates never reach upgraded DBs. Add idempotent `migrateMessageTemplates()` and resolve admin template ids **by Name at runtime** (autoincrement ids can't be hardcoded), threading resolved ids into the config + settings.
- `send-sms` templateId→ReminderType coupling: admin send must pass ReminderType explicitly, never route through the id==1/2 switch.
- Template-validation relaxation is a **three-site** change (`Program.cs` POST ~2073 + PUT ~2111 + React ~84-86); no `type` column to branch on — decide keep `{שם}`+`{תאריך}` mandatory for admin, or add a discriminator.
- `parity-lint.mjs` does not cover a new `ShiftTypes` value-set — requires a real lint code edit (not just the exempt list).
- UI: per-week grouped view should reuse `ShiftsManagementPage` grouping + Chevron nav (NOT `CanceledShiftsPage`, which is a flat monthly table); the admin create dialog (multi-select + save / save+SMS) is genuinely new UI, not a reuse of the operational Add-Volunteer flow.
- Authorization split (Admin vs SystemManager read-only) must be specified for each new admin endpoint + mirrored via `isReadOnly` on the new settings page.

## P2 — polish

- Enforce server-side `HH:mm` zero-pad at every group-key write site (raw string equality splits buckets on `9:00` vs `09:00`).
- The 5 new placeholders require extending the Android `buildMessage` **signature** (flat primitives today), not just `.replace` calls; `{שם מלא}` already diverges .NET vs Android (avoid depending on it).
- Rename touches three distinct strings (menu sub-item, page `<h1>`, parent group) + the template-hint line — be explicit to avoid a half-rename; keep sub-item id/path stable.
- Expand the isolation list to a per-endpoint table (13 routes × 2 platforms) incl. the two Android SAME_DAY dedup call sites.

## Correctness confidence

- **Scheduler timing: HIGH — correct.** `DaysBeforeShift=1` + strictly-after `NextWorkingDay` half-open window puts each shift in exactly one firing day's window; the `SmsLog(ShiftId, 'AdminAdvance')` NOT-EXISTS check is the true idempotency guard. **Depends on P0-1 being fixed** so the run-log INSERT persists.
- **Cross-type isolation: NOT provably complete as written** until P0-2 is fixed and the isolation list is expanded to every by-date/group/canceled/import load on both platforms.

## Bottom line

The plan will be correct, will work, and will be production-ready **after**: (1) P0-1 resolved (recommend in-`SchedulerConfig` admin row + operational-path filtering), (2) P0-2 import-delete filter added, (3) the isolation list completed per-endpoint, and (4) the consolidated open decisions confirmed. Do not begin implementation until P0-1 and P0-2 are settled on paper.

## Consolidated decisions to confirm

1. Admin advance config: **in-`SchedulerConfig` row** (recommended, per the FK) vs separate table + separate run-log.
2. Shift-type discriminator: **column `ShiftType` on `Shifts`** (recommended) vs separate table.
3. Group key `(Date, ShiftTime, Description)` accepted (recommended) vs `ShiftGroupId` column.
4. Per-volunteer icon when shift is NOT today: **assignment template** (recommended) / disabled / other.
5. Template settings storage: **new .NET `AppSettings` table mirroring Android** (recommended); templates resolved by Name on upgrade.
6. Template validation for admin: keep `{שם}`+`{תאריך}` mandatory (simplest) vs add a discriminator.
7. New `AdminAdvance` ReminderType (recommended) vs reuse `WeekdayAdvance`.
8. "Today" message shows vehicle location via explicit `{מיקום רכב}` only (recommended).
9. Authorization: reads = CanManageMessages, config/settings writes = AdminOnly (recommend); mirror read-only for SystemManager.
